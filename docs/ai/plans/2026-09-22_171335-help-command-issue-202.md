# Add `/help` command with runtime auto-discovery (Issue #202)

**Goal:** Add a single `help.md` OpenCode command that, at runtime, enumerates every installed command, skill, and agent and renders them grouped by workflow (commands/skills) and role (agents), with no hardcoded lists.

**Architecture:** A single command file (`base/opencode/commands/help.md`) instructs the `planner` agent to read `.opencode/commands/*.md`, `.opencode/skills/*/SKILL.md`, and `.opencode/agents/*.md` frontmatter live and render a grouped reference. Grouping is metadata-driven: commands and skills carry a canonical `metadata.workflow` key, agents group by `mode`. Because `syncManagedTree` copies commands/skills **verbatim** (verified in `cli/src/lib/manifest.ts` — only agents are transformed with permission injection), a `metadata.workflow` field added to `base/opencode/**` survives install to consuming repos. No companion skill, no TypeScript, no installer changes.

**Tech Stack:** Markdown + YAML frontmatter (OpenCode command/skill/agent format). No code.

**Scope classification:** `multi-task`

## Locked decisions (from planning Q&A)

1. **Grouping = metadata-driven.** Add a canonical `metadata.workflow` field to all commands and normalize all skill `metadata.workflow` values to the same vocabulary.
2. **Single command file, no companion `help` skill.** Discovery/render instructions live directly in `help.md`.

## Canonical workflow vocabulary (locked)

| Key | Purpose | Members (commands / skills) |
|-----|---------|------------------------------|
| `init` | Get a repo ready | `/init` |
| `intent` | Request → bounded intent | `/intent`, `intent` |
| `plan` | Intent → task plan | `/plan`, `plan` |
| `issue` | Shared GitHub issues | `/issue`, `shared-task` |
| `deliver` | Implement plan task-by-task | `/load-plan`, `/implement-task`, `/review-task` |
| `memory` | Durable `docs/ai/` memory | `/memory`, `ai-memory`, `memory-maintenance` |
| `ponytail` | Reuse-first discipline | all `/ponytail*` commands + all `ponytail*` skills |
| `triage` | Error/bug routing | `/triage`, `triage` |
| `authoring` | Authoring ai-config artifacts | `create-skill` |
| `meta` | The guide itself | `/help` |

Display order is the table order above (`init` first, `meta` last). Agents are grouped separately by `mode` (`primary` then `subagent`), not by workflow.

### Task 3: Create `help.md` command and validate end-to-end

**Objective:** Add the `help.md` command that performs runtime discovery and grouped rendering, then verify the full surface.

**Files:**
- Create: `base/opencode/commands/help.md`
- Validate: whole `base/opencode/{commands,skills,agents}` surface

**Step 1: Establish expected behaviour**

Typing `/help` in an ai-config-installed repo renders: (1) a "start here" pointer, (2) all commands grouped by `metadata.workflow` in canonical order, (3) all skills grouped by `metadata.workflow`, (4) all agents grouped by `mode`. New commands/skills/agents appear automatically with no edit to `help.md`.

**Step 2: Add or update validation**

No code test (markdown-only feature). Validation is manual render + a completeness check: `help.md` discovery targets `.opencode/commands/*.md`, `.opencode/skills/*/SKILL.md`, `.opencode/agents/*.md`, so confirm those directories exist in an installed repo and the file counts match (16 commands incl. `help`, 13 skills, 6 agents).

**Step 3: Write minimal implementation**

Create `base/opencode/commands/help.md` with this exact content:

```markdown
---
description: Guide users across every ai-config command, skill, and agent, auto-discovered at runtime.
agent: planner
metadata:
  workflow: meta
---

Discover and render a reference to every ai-config command, skill, and agent installed in this repository. Do the discovery live — never hardcode the lists.

## Discovery

Enumerate (use `rg`/`glob`, do not assume a fixed set):

- Commands: `.opencode/commands/*.md`
- Skills: `.opencode/skills/*/SKILL.md`
- Agents: `.opencode/agents/*.md`

For each file read ONLY the YAML frontmatter and extract:

- Commands: `description` and `metadata.workflow` (fallback to `agent` if `workflow` is absent).
- Skills: `name`, `description`, `metadata.workflow`.
- Agents: `description` and `mode` (`primary` or `subagent`).

## Render

1. **Start here** — one line pointing to `/intent` as the entry point, then the flow: intent → plan → issue → deliver → memory.
2. **Commands** — grouped by `metadata.workflow` in canonical order (`init`, `intent`, `plan`, `issue`, `deliver`, `memory`, `ponytail`, `triage`, `authoring`, `meta`). Each entry: `/command` + one-line description.
3. **Skills** — grouped by `metadata.workflow`, same canonical order. Each entry: skill name + one-line description.
4. **Agents** — grouped by `mode`, primary agents first then subagents. Each entry: agent name + `mode` + one-line description.

## Rules

- Discover at runtime; new commands/skills/agents appear automatically.
- If a file lacks `metadata.workflow`, list it under a final `uncategorized` group rather than dropping it.
- Keep every description to one line.
```

**Step 4: Run test to verify pass**

1. Confirm `help.md` frontmatter parses and its `metadata.workflow: meta` matches the vocabulary.

Manual render probe — invoke `/help` (or read the files directly) and confirm: 16 commands, 13 skills, 6 agents all appear; commands grouped per the Task 1 mapping; skills per the Task 2 mapping; agents split primary (`planner`, `delivery`, `troubleshooter`) vs subagent (`architect`, `code`, `research`).
3. Drift check (optional, cheap): confirm every command and skill file reports a canonical `workflow` key (rerun the Task 1/Task 2 commands).
