# ADR-0009: Unified Project-Level Managed File Format

Date: 2026-06-10
Status: Accepted

## Context

The current managed-file system uses three distinct marker mechanisms to track which files and directories in a consuming repository were generated by the `ai-config` installer:

1. **Per-file marker** — A sidecar file `<file>.ai-config-managed` containing `generated-by=ai-config-bootstrap` for every managed file created or refreshed by `sync_managed_tree` and `sync_managed_file` in `install/lib/managed_sync.sh`.
2. **Per-directory marker** — A file `.ai-config-managed` (the `MANAGED_DIR_MARKER` constant) created inside every managed directory tree, also containing `generated-by=ai-config-bootstrap`.
3. **Inline header marker** — The `MANAGED_OPENCODE_HEADER` (`// Generated by ai-config bootstrap`) written as the first line of generated `opencode.jsonc` files, checked by `is_managed_opencode_file`.

While functional, this approach has several shortcomings:

- **No version information** — The markers contain no reference to which version of `ai-config` produced the installation, making it impossible for a consumer to know whether their installed output matches a given release.
- **No centralized inventory** — There is no single file listing all managed paths. Cleanup or audit requires scanning the entire installed tree for sidecar files and directory markers.
- **Marker proliferation** — Every managed file produces a sidecar file, adding clutter to the consuming repository's working tree.
- **Limited extensibility** — Adding new metadata (install date, runtime, provider set, checksums) would require changes to all three marker mechanisms.

## Decision

Replace the three-marker approach with a single **project-level managed file** stored at the root of each installed project:

**.ai-config-managed** (one per installed project)

Format (YAML-like key-value):

```
version: 0.1.0
ref: v0.1.0
managed_paths:
  - .opencode/agents/skill.md
  - .opencode/commands/plan.md
  - .opencode/skills/staged-delivery/SKILL.md
  - opencode.jsonc
```

Key design points:

- The file sits at the root of the target repository (for example `<consuming-repo>/.ai-config-managed`).
- `version` records the `ai-config` release version that generated the installation (for example `0.1.0`).
- `ref` is an optional field — present only when the installation was performed with a pinned `--ref` / `-Ref` value (tag, branch, or commit). Records the exact ref used for reproducible installs.
- `managed_paths` lists every path under management, relative to the project root. This includes individual files generated by `sync_managed_file` and all files placed by `sync_managed_tree`.
- The file is created and updated exclusively by the installer (`bootstrap.sh` / `bootstrap.ps1`).
- Consumers must not edit this file manually; doing so may cause the installer to skip or misidentify managed paths.
- Per-file sidecar markers (`.ai-config-managed` suffix) and per-directory markers will no longer be created for new installations.
- The `MANAGED_OPENCODE_HEADER` line in `opencode.jsonc` becomes redundant but is kept for backward compatibility during the transition period; new installs may omit it.

## Supersedes

This ADR supersedes the per-file sidecar marker approach (`is_managed_file` and per-file `.ai-config-managed` creation) and the per-directory marker approach (`is_managed_dir` and `MANAGED_DIR_MARKER`) described in the installer implementation.

The `MANAGED_OPENCODE_HEADER` check (`is_managed_opencode_file`) remains in force until Phase 2 implementation provides migration tooling.

## Consequences And Tradeoffs

- **Backward compatibility** — Existing installed projects with per-file and per-directory markers remain valid. The new format is used only for fresh installs or manifest-aware re-installs (auto-detected from existing `.ai-config-managed`).
- **Cleaner repository surface** — A single file at project root replaces potentially dozens of sidecar files, reducing clutter.
- **Version-aware installations** — Consuming repositories can inspect `.ai-config-managed` to determine which version of `ai-config` they were last installed from, enabling smoother upgrades.
- **Simpler uninstall** — `rm <path>` for any managed path is safe because the single file lists all managed paths; no need to discover sidecar files.
- **Installer complexity** — The sync functions (`sync_managed_tree`, `sync_managed_file`) must be updated to write and read the new format instead of per-file markers. Migration logic is needed to detect and optionally upgrade existing installations.
- **Read operation cost** — Checking whether a path is managed now requires parsing the project-level file rather than testing for a sidecar file existence. This is negligible for typical install sizes (< 100 paths) but should be benchmarked during implementation.
- **Concurrent install safety** — The same concerns apply as with the current approach; the installer uses file-level locking or sequential operations per project.

## Alternatives Considered

- **Keep the current three-marker system** — Rejected because it lacks version tracking, creates unnecessary clutter, and provides no centralized inventory for cleanup or audit.
- **Use a JSON manifest instead of YAML-like format** — Rejected to keep parsing dependency-free in both Bash and PowerShell. A simple line-oriented key-value format is trivially parseable in both shells.
- **Store markers in a hidden directory (`.ai-config/`)** — Rejected because the current approach already places markers directly at the project root or alongside managed files; introducing a new hidden directory adds complexity without a clear benefit.
- **Embed version inside each managed file** — Rejected as too invasive; it would require every managed file to carry a version header, which risks conflicts with file format expectations (for example JSONC, Markdown frontmatter).
